# Data Model & Schema Specifications: Feature 012

## 1. Tenant Sequence Schema

Proposed table: `tenant_sequences`.

| Column | Type | Nullability / rule | Purpose |
|---|---|---|---|
| `id` | UUID | primary key | Technical row identity if repository model conventions require it. |
| `organization_id` | UUID | not null, FK to `organizations.id`, restrict/cascade per existing tenant model policy | Tenant owner of the sequence. |
| `namespace` | String(32) | not null | Stable internal namespace such as `TRX`, `JE`, `PRJ`, `DOC`, `INV`, `BIL`, `ADV`, `REL`, `MM`, or `SET`. |
| `scope_key` | String(32) | not null | Calendar year string (e.g. `'2026'`) for year-coded namespaces; explicit `'GLOBAL'` sentinel for tenant-global non-year namespaces (`SET`). Strictly non-null; PostgreSQL NULL semantics are prohibited. |
| `next_value` | Integer / BIGINT | not null, positive, default 1 | Next number to reserve; exact type must cover the largest existing padding range. |
| `created_at` | timezone datetime | not null | Audit metadata. |
| `updated_at` | timezone datetime | not null | Audit metadata. |

Required uniqueness: `UNIQUE (organization_id, namespace, scope_key)` named `uq_tenant_sequences_org_ns_scope`.
All three columns are strictly `NOT NULL`, guaranteeing deterministic uniqueness across all supported database engines without NULL-equality divergence.

### Allocation transaction

The allocator receives `(organization_id, namespace, scope_key)` where `scope_key` is either a 4-digit calendar year (e.g. `'2026'`) or `'GLOBAL'` (for `SET`), and returns the reserved integer plus rendered code metadata. It must execute in the caller’s `AsyncSession` transaction:

1. Validate organization and namespace input.
2. Lock the existing scope row with `SELECT ... FOR UPDATE`.
3. If the row does not exist, insert it using an insert-on-conflict/bootstrap loop that handles concurrent first allocation without duplicate scope rows.
4. Increment `next_value` atomically and return the prior value.
5. Render the existing format in the service boundary (`SET-000001`, `TRX-2026-000001`, etc.).
6. Let the business record and any journal/posting work commit in the same transaction.

A rollback may leave a numeric gap only if the chosen database operation commits the allocation independently; the preferred counter-table design keeps allocation in the caller transaction. In all cases, a number must never be reused after a committed business record or used for two committed records.

## 2. Existing Entity Constraints

### Confirmed changes

| Table | Current | Target |
|---|---|---|
| `money_movements` | global unique `movement_code` | `UNIQUE (organization_id, movement_code)` named `uq_money_movements_org_code` |
| `settlements` | global unique `settlement_code` | `UNIQUE (organization_id, settlement_code)` named `uq_settlements_org_code` |
| `fixed_assets` | global unique `asset_code` | `UNIQUE (organization_id, asset_code)` named `uq_fixed_assets_org_code` |

The SQLAlchemy models must remove `unique=True` from these columns and declare matching `UniqueConstraint` entries in `__table_args__`.

### Constraints that remain unchanged

Transaction code, journal entry number, project code, document code, invoice code, bill code, advance code, retention-release code, chart-of-account code, and accounting-period name already use tenant-composite uniqueness and must remain so. Organization slug, WhatsApp sender phone, and other identifiers that resolve tenant context before a tenant is known remain globally unique.

`DocumentSession.session_code` remains global under this feature because its global generation/constraint semantics align. Its truncated entropy is a separately tracked risk, not an implicit migration request.

## 3. Alembic Migration Strategy

Proposed revision: one new revision after `021_fixed_asset_enhancements`, with the actual revision identifier selected by repository convention during implementation.

### Upgrade preflight

The migration must fail closed if any of these checks return rows:

```sql
SELECT organization_id, movement_code, COUNT(*)
FROM money_movements
GROUP BY organization_id, movement_code
HAVING COUNT(*) > 1;

SELECT organization_id, settlement_code, COUNT(*)
FROM settlements
GROUP BY organization_id, settlement_code
HAVING COUNT(*) > 1;

SELECT organization_id, asset_code, COUNT(*)
FROM fixed_assets
GROUP BY organization_id, asset_code
HAVING COUNT(*) > 1;
```

It must also verify that the current global constraints exist under the live database’s actual names before dropping them. Do not assume names generated by `unique=True`; inspect `pg_constraint`/Alembic metadata on the disposable target.

### Upgrade order

1. Execute duplicate-tuple and expected-constraint preflight.
2. Create each composite unique constraint.
3. Drop the corresponding global single-column constraint only after the composite constraint exists.
4. Commit as one Alembic migration transaction where supported by PostgreSQL.
5. Verify same-tenant duplicates fail and cross-tenant same-code inserts succeed.

### Downgrade

Before restoring global constraints, run a global-duplicate preflight. If any code is shared across organizations, abort downgrade without deleting or renumbering data. Only then create the old global constraints and remove the composite constraints. The downgrade must be tested on a disposable schema.

## 4. Concurrency and Locking Mechanics

PostgreSQL row-level locking is authoritative. `FOR UPDATE` on a stable counter row serializes allocations for one `(organization, namespace, scope)` while allowing unrelated tenants/scopes to proceed concurrently. The first-row path requires conflict-safe bootstrap; a plain select-then-insert is not sufficient.

The allocator must not commit independently of the business transaction, must not use a process-local lock, and must not catch a uniqueness exception and continue using the same failed session transaction. Retry handling must start a clean transaction/session unit and be bounded.

## 5. Historical Data Compatibility

The constraint relaxation is non-destructive in principle because existing global uniqueness implies composite uniqueness. The preflight remains mandatory because live schemas may differ from expected migrations. No existing code values, posted records, journals, or protected documents may be modified.
